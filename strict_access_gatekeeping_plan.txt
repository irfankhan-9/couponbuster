# Implementation Plan: Strict Syndicate Access & Gatekeeping

## 1. Objective
To implement a "Zero-Bypass" security architecture for syndicate leagues. No user shall be able to view pick forms, leaderboards, or financial pots for a league unless they have a verified 'approved' status in the membership record. This prevents "cheating" via URL manipulation or inspecting element states.

## 2. Phase 1: The "Leagues" Page Button Matrix
The `pages/Leagues.tsx` will be updated to enforce a strict 3-tier button logic based on the user's relationship with the league:

- **State A: Anonymous (Not a Member)**
    - **Action:** Display the "Join League" button.
    - **Visual:** Primary Slate-900 action button.
    - **Security:** Clicking triggers the `JoinLeagueModal`.
- **State B: Awaiting Verification (Pending Status)**
    - **Action:** Display a disabled "Approval Pending" badge.
    - **Visual:** Soft amber/yellow background with a lock icon.
    - **Security:** Non-clickable. Prevents multiple spam requests.
- **State C: Verified Member (Approved Status)**
    - **Action:** Display the "Go to Dashboard" button.
    - **Visual:** High-contrast Emerald-600 outline button.
    - **Security:** Link leads to the protected league URL.

## 3. Phase 2: The "Dashboard Guard" (Cheating Prevention)
The `pages/Dashboard.tsx` will act as a strict gatekeeper. Even if a user manually types `/league/l123` into their browser, the following sequence will execute before ANY data is rendered:

1. **Identity Check:** Resolve the current `leagueId` from the URL parameters.
2. **Membership Validation:** Query the `MOCK_MEMBERS` source of truth for a record matching both the `leagueId` AND the `CURRENT_USER_ID`.
3. **Strict Redirection:**
    - **If no record exists:** The app will trigger an immediate `<Navigate to="/leagues" />`. The user never sees the dashboard content.
    - **If status is 'rejected':** Immediate redirect to `/leagues` with a "Access Denied" state.
    - **If status is 'pending':** Render a high-fidelity "Access Restricted" splash screen with a countdown or "Waiting for Admin" message. The Pick Form and Leaderboard remain unmounted in the DOM.

## 4. Phase 3: Admin Approval Integrity
In `pages/Admin.tsx`, the approval process is the only key that unlocks the door:

- **Approval Action:** Mutates the user's status to 'approved' in the mock database.
- **Push Changes Sync:** When "Push Changes" is clicked, it forces a global re-evaluation of the membership state. 
- **Integrity Check:** The Admin panel will explicitly show the "Active/Max" capacity. Once a league is full, the "Join" button globally switches to "League Full" for everyone else, preventing over-subscription.

## 5. Phase 4: Visual & UX Consistency
- **Loading States:** During the "Push Changes" sync, show a "Verifying Permissions..." spinner to reinforce the feeling of a secure, bank-level transaction.
- **Transitions:** Use smooth fade-outs for the "Pending" screen when it transitions to the "Active" dashboard to provide a satisfying "unlock" experience for the user.
- **Feedback:** If a user is rejected, provide a clear but professional "Request Declined" notification to ensure they understand why access was not granted.

## 6. Verification Checklist (Anti-Cheat)
1. **Direct URL Test:** Attempt to navigate to an unjoined league (e.g., `/league/l999`). Result: Automatic kick-back to the leagues list.
2. **Pending Bypass Test:** Attempt to view picks for a league where status is 'pending'. Result: Dashboard renders ONLY the "Access Restricted" screen; `PickForm` is not in the DOM.
3. **Approval Flow:** Admin approves -> Admin pushes -> User refreshes. Result: "Go to Dashboard" button appears instantly.
4. **Full League Test:** Fill a league to max capacity. Result: "Join" button disappears for all other users.
